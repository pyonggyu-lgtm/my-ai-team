## 1. Socket.IO 4 클라이언트 재연결 기본 동작

**결론**
1. 기본값은 자동 재연결 켬(`reconnectionAttempts: Infinity`, 대기 1초→최대 5초, 무작위 계수 0.5). 이벤트 이름: 소켓 `connect`(재연결 성공 때마다 다시 발생)·`disconnect`(reason)·`connect_error`, 재연결 시도 상세는 **`socket.io.on("reconnect_attempt" | "reconnect" | "reconnect_error" | "reconnect_failed")`**(Manager 쪽, 소켓 쪽 아님).
2. `auth`는 재연결 핸드셰이크마다 다시 보낸다. 객체면 같은 값, **함수형 `auth: (cb) => cb({ token, groupId })`면 매 시도 직전에 호출**되므로 토큰·그룹이 바뀔 수 있는 우리 앱은 함수형이 안전하다.
3. **자동 재연결이 안 되는 경우 두 가지(★ 중요)**: (a) 서버 `io.use()` 미들웨어가 거부한 `connect_error`(우리의 `UNAUTHORIZED`/`FORBIDDEN`), (b) `disconnect` reason이 `"io server disconnect"`(서버가 `disconnect(true)` 한 경우 = 우리의 "나가기" 처리). 이때는 클라이언트가 `socket.connect()`를 직접 불러야 하는데, 401/403이면 불러서는 안 된다(토큰 지우고 `signedOut` 신호). 서버 프로세스가 재시작되면 `transport close`/`ping timeout`으로 끊긴 뒤 자동 재연결되고, **새 `socket.id`·방(room) 가입 초기화** 상태로 들어오므로 서버 `connection` 핸들러에서 `group:{gid}` 방에 다시 넣는 지금 설계가 맞다. `connectionStateRecovery`(4.6+)는 단일 서버 재시작 시 메모리가 사라져 복구되지 않으니(`socket.recovered === false`) 쓰지 말고, **재연결 때마다 `GET /state`** 로 메우는 지시서 방식을 유지.

참고: 끊긴 동안 `socket.emit()`은 메모리 버퍼에 쌓였다가 재연결 때 나간다. 우리는 쓰기를 HTTP로 하므로 소켓 emit은 안 쓰면 영향 없음.

**근거**
- https://socket.io/docs/v4/client-socket-instance/
- https://socket.io/docs/v4/client-options/
- https://socket.io/docs/v4/offline-behavior/
- https://socket.io/docs/v4/connection-state-recovery/

## 2. iOS Safari·홈 화면 앱의 백그라운드 복귀와 WebSocket

**결론**
1. 백그라운드로 가면 수 초~30초 안팎에 페이지 JS가 멈추고 소켓이 OS에 의해 끊기거나 죽은 채 남는다. 복귀 직후 `readyState`가 아직 `OPEN`인 **유령 연결**이 흔하고, 메모리 압박이면 페이지가 통째로 새로 로드되기도 한다. (정확한 유예 시간은 iOS 버전·기기마다 달라 확정 수치로 믿지 말 것 ★)
2. 끊긴 동안의 서버 이벤트는 재전송되지 않는다(Socket.IO도 마찬가지). 그래서 **돌아올 때 `GET /state`를 다시 받아야 하며, 이것이 유일한 정합성 수단**이다. 우리 `rev` 비교(큰 것만 반영)와 잘 맞는다.
3. 권고: `document`의 `visibilitychange`(`visible`일 때)와 `window`의 `pageshow`(`event.persisted`, 뒤로가기 캐시 복원)에서 ① `GET /state` ② 소켓이 끊겨 있으면 `socket.connect()`, 연결돼 보이면 그대로 두고 Socket.IO 자체 ping에 맡기되 `GET /state` 응답에 실패하면 `socket.disconnect().connect()`로 강제 재연결. 진행 중인 요청이 있으면 중복 호출하지 않게 한 번에 하나만. 재연결 `connect` 직후에도 한 번 더 `GET /state`(지시서와 동일).

**근거**
- https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API
- https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API
- https://developer.chrome.com/docs/web-platform/page-lifecycle-api
- (iOS 유예 시간·유령 연결은 Gemini 설명이며 WebKit 공식 문서로 직접 확인되지 않음. 근거가 약한 부분이므로 폰 실기 확인은 배포 후 사장님 몫.)

## 3. `navigator.onLine` / `online`·`offline` 이벤트를 믿어도 되는가

**결론**
1. **`false`는 믿어도 되고(확실히 오프라인), `true`는 믿으면 안 된다.** 공유기까지만 연결·캡티브 포털·VPN/Docker/WSL 같은 가상 어댑터·방화벽·서버 장애에서도 `true`가 나온다. (이 공장이 WSL이라 개발 PC에서도 재현될 수 있음.)
2. 오프라인 판정은 **실제 요청의 성공·실패**로 한다: `fetch`의 네트워크 오류(`TypeError`)·타임아웃(`AbortController`) 또는 Socket.IO `disconnect`/`connect_error`. `navigator.onLine`과 `online`/`offline` 이벤트는 "지금 확인해 보라"는 **보조 신호**로만 쓴다.
3. 권고: 연결 상태 = 소켓 `connect` 여부 AND 마지막 요청 성공 여부. `online` 이벤트나 `visibilitychange`가 오면 `GET /state`(또는 `/api/health`, `cache: "no-store"`)로 실제 확인 후 대기열(outbox) 비우기 시작. `navigator.onLine === false`면 요청 전에 바로 OFFLINE 처리해도 안전. 시험은 Playwright `context.setOffline(true)`로 가능(지시서와 동일). 설계 4.2 표 첫 줄에 `GET /api/health`(→ `{ ok, now, today }`, 단계 2)가 이미 있으므로, 가벼운 연결 확인은 이 API를 쓴다(인증 없이 호출 가능, 새로 만들 필요 없음).

**근거**
- https://developer.mozilla.org/en-US/docs/Web/API/Navigator/onLine
- https://developer.mozilla.org/en-US/docs/Web/API/Window/online_event
- https://developer.mozilla.org/en-US/docs/Web/API/Window/offline_event
- https://html.spec.whatwg.org/multipage/system-state.html#browser-state

## 4. better-sqlite3 + WAL, Node 프로세스 1개

**결론**
1. API가 전부 동기라 쿼리 중에는 이벤트 루프가 멈추고, 한 프로세스·하나의 `db` 객체면 요청끼리 자연히 한 줄로 처리돼 프로세스 안에서는 `SQLITE_BUSY` 경합이 없다. 무거운 쿼리만 피하고, `db.prepare()`는 시작 때 한 번 만들어 재사용. **`db.transaction(fn)` 안에서 `async`/`await` 금지**(await 중 다른 요청이 끼어들거나 먼저 커밋됨). 예외가 나면 자동 롤백 후 다시 던져지고, 트랜잭션 안에서 다른 트랜잭션 함수를 부르면 SAVEPOINT로 중첩된다. 우리 "확정 + 넘김 비우기 + rev+1" 한 트랜잭션 설계에 맞음. 동시 확정 시험(③)은 단일 프로세스라 순서대로 처리되므로 "먼저 온 것이 201, 다음이 409"가 결정적으로 나오는 것이 정상. `db.transaction(...).immediate(...)`는 쓰기 락을 처음부터 잡는다.
2. 기본 `busy_timeout`은 5000ms(생성자 `timeout`). 다른 프로세스(DB 도구·백업 스크립트)가 같은 파일에 오래 쓰면 이 시간 동안 **서버 전체가 멈춘다**. 운영 중 sqlite3 CLI로 쓰기 작업을 하지 말 것. 서버 종료(`SIGINT`/`SIGTERM`) 때 `db.close()`로 체크포인트. 로컬 디스크에만 둔다(EFS 등 네트워크 드라이브 금지). `data/` 폴더 자체에 쓰기 권한 필요(`-wal`·`-shm` 생성). `-wal`/`-shm`을 손으로 지우지 말 것.
3. **백업은 `db.backup(경로)`(Promise, 페이지 단위라 서비스 중에도 일관된 스냅샷) 또는 `VACUUM INTO '경로'`** 로 한다. WAL 모드에서 `.db` 파일만 `cp`하면 최신 커밋이 빠지고, 세 파일을 같이 복사해도 쓰는 중이면 깨질 수 있다. (`VACUUM INTO`는 동기라 커져도 DB가 작아 문제없을 규모, 백업 자동화는 4단계 이후 과제.)

**근거**
- https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md
- https://github.com/WiseLibs/better-sqlite3/blob/master/docs/performance.md
- https://www.sqlite.org/wal.html

| 항목 | 반영 제안 |
|---|---|
| 소켓 `auth` | 함수형 `auth: (cb) => cb({ token, groupId })` |
| `connect_error`(UNAUTHORIZED/FORBIDDEN)·`io server disconnect` | 자동 재연결 안 됨 → 토큰 지우고 `signedOut` 신호, `socket.connect()` 호출 금지 |

| DB | 트랜잭션 안 await 금지, 종료 시 `db.close()`, 백업은 `.backup()` |
