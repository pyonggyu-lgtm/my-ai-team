# 2단계 브라우저 2개 시나리오 (진사, 묶음 G)

설계 3.3의 시나리오 1~8을 브라우저 창 2개(A·B, 390×844 폰 크기)로 실행한다. 두 창은 **서로 다른 브라우저 맥락**이라 저장소·로그인이 따로다(서로 다른 폰처럼).

## 실행

```
LD_LIBRARY_PATH=$(cat /home/claude/chrome-deps/ldpath.txt) FONTCONFIG_FILE=/home/claude/chrome-deps/fonts.conf node tests/e2e/scenarios_g.mjs
```

- 서버는 스크립트가 `server/index.js`의 `createServer`를 불러 **임시 DB(`os.tmpdir()`)·임의 포트**로 직접 띄운다(`staticDir`=`client/`). 끝나면 서버를 닫고 임시 폴더를 지운다. `npm run dev`·8080 서버는 필요 없다. 서버 파일은 고치지 않는다.
- 결과: `docs/design/2단계_캡처/G_result.json`(항목별 통과·관측값), `G_api.json`(시나리오 8의 `GET /history`·`/stats` 응답, 토큰 없음), 캡처 `G-01…G-16-*.png`. 실패하면 `G-실패-A/B.png`.
- 종료 코드 0 = 전부 통과. 앱은 고치지 않는다(실패하면 항목·관측값으로 보고).
- 한 번에 약 1분(회전이 5초씩 여러 번).

## 시나리오와 확인 항목

| # | 내용 | 확인 |
|---|---|---|
| 1 | A가 그룹 만들기 → 초대 링크를 B가 열고 닉네임 입력 → 서로 멤버 목록에 | 시작 화면이 처음 보임 · 만든 뒤 닫힘·메뉴판 '점심' · 초대 코드 6자리(헷갈리는 글자 없음)·링크 형식 · B는 `?join=`으로 열면 참여 쪽 + 코드 채움 + 미리 보기(그룹 이름·"지금 1명이…") · 참여 뒤 주소의 `?join=` 지워짐 · 열려 있던 A의 멤버 목록에 B가 4초 안에 나타남 · 두 창 목록(만든 사람·나 표시) · 토큰 원문이 화면 본문에 없음 |
| 2 | A가 메뉴 추가·끄기 → B 3초 안에 | 추가한 메뉴가 B에 보임 · 끈 메뉴가 B에서 꺼짐 · 개수 표시 같음 |
| 3 | A가 돌리는 중 B가 메뉴 추가 | A는 `body.busy`·목록에 아직 없음(회전 그대로) → 끝난 뒤 3초 안에 목록에 반영 |
| 4 | A가 다시 돌리기 | B의 그 메뉴에 "오늘 넘김" 태그(3초 안) · A의 다시 돌린 결과는 넘긴 메뉴가 아님 |
| 5 | A가 확정 | B의 상단 배지(`#today`)가 3초 안에 같은 메뉴 · **B에는 결과 카드가 뜨지 않음** · B에 "에이님이 …확정했어요" 알림, A에는 없음 |
| 6 | B가 같은 메뉴판을 확정 시도 | 덮어쓰기 확인창 문구 `에이님이 {메뉴}로 확정했어요. 바꿀까요?` · 처음 포커스 "그대로 두기" · 그대로 두기 → 기록은 A 확정 그대로 |
| 7 | A 오프라인(`context.setOffline(true)`)에서 확정, 그동안 B가 다른 메뉴로 확정(바꾸기) → A 다시 연결 | 끊김 띠·`is-offline`·띠 문구 · 오프라인 메뉴 추가 막힘("연결되면 바꿀 수 있어요.") · 오프라인 확정 알림·대기열 1건 · 재연결하면 덮어쓰기 확인창(B의 닉네임·B가 고른 메뉴, "내가 고른 메뉴"=오프라인에서 고른 메뉴) · 바꾸기 → 두 창 배지 같음 · 띠 사라짐 |
| 8 | 두 창의 기록 화면과 `GET /history` 응답 비교 | 두 창의 날짜·메뉴·막대가 같음 · 확정한 사람이 같은 사람(각 창의 "나"만 다름) · 두 토큰의 `/history`·`/stats` 응답이 완전히 같음 · 오늘 기록 = A가 마지막에 고른 메뉴(에이)·그날 1건 |
| 공통 | 콘솔 오류·페이지 오류·실패한 요청·4xx/5xx 응답 | 아래 규칙대로 거른 뒤 0건 |

## 오류·실패 요청 거르는 규칙 (지시서)

- `console.error`("Failed to load resource" 제외)·`pageerror`는 하나도 허용하지 않는다.
- **`requestfailed`는 응답 204를 받은 요청의 `net::ERR_ABORTED`만 제외**한다(Chromium이 빈 응답을 이렇게 알리는 경우가 있음). 그 밖의 실패는 전부 오류.
- 오프라인 구간(시나리오 7에서 A가 끊긴 동안)의 A의 `requestfailed`(`ERR_INTERNET_DISCONNECTED`)는 **예상된 것**으로 따로 세어 `G_result.json`의 `expectedOffline`에 남기고 오류로 치지 않는다.
- 4xx/5xx 응답은 `/favicon.ico` 404(3단계에서 해결)와 **설계된 확정 409**(`POST /api/boards/:id/history`, 덮어쓰기 확인용)만 제외한다. 409는 정확히 B 2번(시나리오 6·7) + A 1번(시나리오 7)이어야 통과(항목으로 확인).

## 준비 코드 (0·1단계 시험)

0·1단계 시험은 새 화면을 열 때 시작 화면이 가로막지 않도록 `tests/e2e/_lib.mjs`의 `open()`이 `hanjan.v1.device`에 `mode:"solo"`(store-local의 `getMode/setMode`와 같은 값)를 넣는다(`solo:false`를 주면 안 넣음 — 2단계 시나리오가 사용). 시험 내용·기준은 그대로.
