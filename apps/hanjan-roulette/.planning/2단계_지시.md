## 확정된 세부 규칙 (설계 3.3·4·5장을 구체화 — 여기와 다르게 하려면 먼저 보고)

### 설치와 폴더
- 앱 폴더(`apps/hanjan-roulette/`)에서: `npm install express socket.io better-sqlite3` 와 `npm install -D socket.io-client`. 설치된 정확한 버전을 보고에 적는다. `package-lock.json`은 남긴다.
- `better-sqlite3` 빌드가 실패하면(기계어 빌드 도구 부족 등) **다른 것을 설치하거나 `node:sqlite`로 바꾸지 말고** 오류 끝 20줄과 함께 진록에게 보고.
- `apps/hanjan-roulette/.gitignore`(진오 소유)에 `data/`, `*.db`, `*.db-wal`, `*.db-shm`. 개발용 DB는 `data/hanjan.db`, 시험용 DB는 `os.tmpdir()` 아래 임시 파일(시험 끝나면 닫기만, 지우기는 tmpdir 안이므로 허용).
- `package.json` 스크립트: `"test"`는 그대로(단위), `"test:server": "node --test \"tests/server/*.test.js\""`, `"dev": "node server/index.js"`(포트 `PORT` 기본 3000, 개발용으로 `client/`를 정적 제공).

### 서버 뼈대 `server/index.js`
- `export async function createServer({ dbPath, now = () => new Date(), staticDir = null, rateLimit } = {})` → `{ app, httpServer, io, db, listen(port=0) → 실제 포트, close() }`. 시험은 `listen(0)`으로 임의 포트, 내장 `fetch`로 호출(supertest 금지).
- 파일을 직접 실행했을 때만 `listen(process.env.PORT || 3000)` + `staticDir = client/`.
- `app.set("trust proxy", "loopback")` (Nginx가 같은 서버에 있으므로 루프백만 믿음). `express.json({ limit: "16kb" })`, 단 `POST /api/groups`만 `"1mb"`(옮기는 기록 때문).
- 오류는 한 곳에서 `{ error: { code, message } }`로. 알 수 없는 오류는 500 `INTERNAL` "잠시 후 다시 시도해 주세요." — 스택·요청 본문·Authorization 헤더를 로그에 남기지 않는다(메서드·경로·상태 코드만).
- 서버가 `../client/js/kst.js`, `templates.js`, `pool.js`, `records.js`를 import 해서 날짜·제한값·템플릿·어제 메뉴·기록 자르기·통계를 **새로 만들지 않고 그대로** 쓴다. `today`는 언제나 `todayKST(now())`.

### DB `server/db.js` (better-sqlite3, 동기)
- `openDb(path)` → WAL(`journal_mode = WAL`), `foreign_keys = ON`, 설계 5장 테이블을 `CREATE TABLE IF NOT EXISTS`로. 외래 키는 `ON DELETE CASCADE`(메뉴판 삭제 시 items·skipped·history 함께).
- id: `crypto.randomBytes(9).toString("base64url")` (12자). 시각 열은 ISO 문자열, `date`는 `YYYY-MM-DD`.
- `boards.rev`: 그 메뉴판(또는 items·skipped·그 메뉴판 history)이 바뀌는 **모든 쓰기 트랜잭션 안에서** `rev = rev + 1`, `updated_at` 갱신.
- 확정: `confirm({ boardId, date, name, memberId, overwrite, confirmedAt })` 하나의 `db.transaction` 안에서 — 같은 `(board_id, date)`가 있고 `overwrite`가 false면 `{ ok:false, existing:{ name, nickname, confirmedAt } }`, 아니면 INSERT 또는 UPDATE, 그리고 `date`가 오늘이면 그 메뉴판의 오늘 skipped 삭제, rev+1. 반환에 `replaced`(덮어쓴 기존 값 또는 null).
- 메뉴판 직렬화 `boardView(boardId, today)` → `{ id, name, resultLead, template, excludeYesterday, sortOrder, rev, items:[{ id, name, isOn, sortOrder }](sortOrder 순), skipped:[오늘 넘긴 이름], confirmed:{ name, nickname, confirmedAt } | null(오늘), yesterday: 어제 확정 메뉴 이름 | null }`. 이벤트·응답 모두 이 모양 하나.
- 제한(16개, 10판, 중복 이름)은 db 함수 안에서도 트랜잭션으로 검사해 동시 요청에도 넘지 않게.
- 시험 `tests/server/db.test.js`: 테이블·WAL 확인, `(board_id,date)` 유일, 확정+넘김 비우기가 한 트랜잭션(중간 실패 시 둘 다 원래대로), rev 증가, 메뉴판 삭제 시 하위 행 삭제, 16·10·중복 제한, 나간 멤버(`left_at`) 기록의 닉네임 유지.

### 인증 `server/auth.js`
- `newToken()` → `randomBytes(32).toString("base64url")`, `hashToken(t)` → SHA-256 hex. DB에는 해시만.
- `requireMember` 미들웨어: `Authorization: Bearer x` → 해시로 멤버 찾기, 없거나 `left_at`이 있으면 401. 경로의 `:gid`, 또는 `:bid`→그룹을 거슬러 올라가 소속이 아니면 403. 없는 id는 404, 남의 그룹 id는 403(설계 4.1 표 그대로. id가 12자 무작위라 짐작이 어려워 존재 여부가 드러나도 괜찮다고 판단). 토큰 확인(401)이 언제나 먼저.
- 초대 코드: 글자 `ABCDEFGHJKMNPQRSTUVWXYZ23456789`(31종, 0·O·1·I·L 제외) 중 `crypto.randomInt`로 6자리, 겹치면 다시. 입력은 대문자로 바꾸고 앞뒤 공백 제거 후 비교.
- 시도 제한: `GET /api/invites/:code`와 `POST /api/invites/:code/join`을 합쳐 **IP당 10분 창에 10번**. 11번째부터 429 `RATE_LIMITED` + `retryAfterSec`. 서버 메모리 `Map`, 주입된 `now()` 사용, 오래된 항목은 정리(메모리 무한 증가 금지). `createServer({ rateLimit: { max, windowMs } })`로 바꿀 수 있게. 두 라우트는 **같은 limiter 객체**를 쓴다.
  - **진육 B 리뷰 후 진록 결정(2026-11-05)**:
    - **틀린 시도(없는 코드 404·닫힌 그룹 404)만 센다.** 맞는 코드로 조회·참여한 것은 세지 않는다. (이 지시서 처음 판의 "맞든 틀리든 센다"는 진록이 덧붙인 해석이었고, 설계 시험 ②"11번 틀리면 429"와도 이쪽이 맞음. 식당 Wi-Fi·통신사 공유 IP에서 여러 명이 한꺼번에 참여해도 막히지 않게.) 이미 10번 틀린 주소는 맞는 코드라도 창이 끝날 때까지 429.
    - **IPv6는 앞 64비트(/64)로 묶어** 하나로 센다(`::ffff:` IPv4 매핑 주소는 IPv4로). IPv4는 주소 하나 그대로.
    - 꽉 찼을 때(`maxEntries` 10000): 기한 지난 항목 → 차단되지 않은 오래된 항목 순으로만 지운다. **차단 중인 항목은 지우지 않는다.** 그래도 자리가 없으면 새 주소는 429(공격 중이라고 보고 닫힌 쪽으로).
    - 초대 코드 정리: `normalize("NFKC")`(전각 글자) + `trim` + 대문자 + 공백·하이픈·대시류 제거(`replace(/[\s\-‐-―−]/g, "")`). 정리 후 6자리·허용 글자가 아니면 DB 조회 없이 404 — **이 경우는 세지 않는다**(진짜 코드일 수 없어 무작위 대입에 도움이 안 되고, 어르신 오타로 막히지 않게. 진육 B 재확인 권고3 → 진록 결정).
    - **전체 실패 상한**(진육 B 재확인 권고1 → 진록 결정): 주소와 상관없이 서버 전체에서 10분 창에 틀린 시도가 300번을 넘으면 창이 끝날 때까지 초대 조회·참여 모두 429. 이미 그룹에 든 멤버의 다른 API에는 영향 없음. `rateLimit: { globalMax }`로 바꿀 수 있게.
    - `isBlocked`는 읽기만 한다(항목 추가·지우기 금지). 최솟값 찾기는 전개 연산 대신 반복문(권고2).
- 시험 `tests/server/auth.test.js`: 해시 고정 길이·원문 불일치, 초대 코드 글자 집합·길이, 시도 제한(10번 통과·11번째 429·10분 뒤 다시 허용, 다른 IP는 별개).

### API `server/routes/groups.js`, `boards.js`, `history.js`
- 설계 4.2 표의 **"단계 2" 행만**. 4단계 행은 만들지 않는다.
- 입력: 문자열은 `trim()` 후 길이 검사(빈 값·초과 → 400 `VALIDATION`). 타입이 틀리면(문자열 자리에 숫자 등) 400. 알 수 없는 필드는 무시. `template`은 `TEMPLATE_IDS` 중 하나.
- 화면 문구(1단계와 같게): "16개까지 넣을 수 있어요.", "이미 있는 메뉴예요.", "메뉴판은 10개까지 만들 수 있어요.", "메뉴판은 1개 이상 있어야 해요."(마지막 메뉴판 삭제 → 400 `VALIDATION`), 만든 사람이 다른 멤버가 남아 있는데 나가기 → 400 `VALIDATION` "다른 멤버가 있으면 만든 사람은 나갈 수 없어요."
- `POST /api/groups`: `importBoards`가 없거나 빈 배열이면 "점심" 템플릿 1개. 있으면 1단계 `getState()` 모양(메뉴판 + 그 메뉴판 `history` 배열)을 받아 같은 검사(10판·16개·길이·중복, 날짜 형식)를 거쳐 옮긴다. 옮긴 기록의 확정한 사람 = 만든 사람. 하나라도 틀리면 400(일부만 옮기지 않음, 한 트랜잭션).
- 확정 `date`: 없으면 오늘. 있으면 오늘 또는 어제만, 아니면 400 `VALIDATION` "연결이 오래 끊겨 확정을 보내지 못했어요." 확정 메뉴 이름이 지금 메뉴판에 없어도 받는다(회전 시작 후 지워진 경우, 설계 3.3).
- **활성 멤버가 0명인 그룹**(만든 사람이 혼자 남아 나간 경우, 진육 A 리뷰 권고5 → 진록 결정): 데이터는 지우지 않는다(삭제는 4단계). 대신 그 그룹은 닫힌 것으로 보고 `GET /api/invites/:code`·`POST .../join`은 404 `NOT_FOUND`("없는 초대 코드예요." — 없는 코드와 같은 응답). 스키마 변경 없음.
- 진육 A 리뷰 권고 반영(묶음 C에서): ① `db.js` 템플릿 기본값이 `undefined`로 덮이지 않게(값이 없으면 템플릿 기본값), ② 어제 메뉴 조회에 `date <= today`(오늘 이전) 조건, ③ 확정 라우트에서 `DATE_RE`·오늘/어제·요청자 = `requireMember`의 멤버만, ④ `importBoards`의 template·이름·메뉴·기록 날짜 형식 검사(하나라도 틀리면 400, 전부 롤백).
- **진육 C 리뷰 권고 → 진록 결정 (C-수정에서 반영)**:

### 클라이언트 `client/js/api.js`, `store-remote.js`
- `store-remote.js`는 **1단계 저장소 약속과 같은 함수 이름·반환 모양**(`getState`, `createBoard` … `subscribe`)을 지킨다. 달라지는 점만:
  - `confirm(boardId, name, { overwrite, date })` → `{ ok:true }` 또는 `{ ok:false, code:"ALREADY_CONFIRMED", existing }`.
  - 오프라인일 때 메뉴·메뉴판 편집 함수는 `{ ok:false, code:"OFFLINE", message:"연결되면 바꿀 수 있어요." }`.
  - 추가: `getGroup()`, `listMembers()`, `leaveGroup()`, `onConnection(listener)`(연결/끊김 표시용).
- localStorage는 여전히 **`store-local.js`의 `getBrowserStorage()`로만** 얻는다(`grep -n localStorage client/js` → `store-local.js`에만 나와야 함). 키: 기기 정보는 `hanjan.v1.device`에 `token`·`groupId`·`memberId` 필드 추가, 마지막 상태 `hanjan.v1.remote.cache`, 대기열 `hanjan.v1.outbox`.
- 대기열에 넣는 것: 확정(누른 날짜 `date` 포함), 넘김 추가, 넘김 비우기 — 이 3가지뿐. 연결되면 들어간 순서대로 하나씩, 409면 멈추고 확인창 요청 신호(`subscribe`로 `{ type:"conflict", boardId, existing, pending }`), 400(오래된 날짜)이면 그 항목을 버리고 알림 신호.
- 재시도: 네트워크 오류인 GET만 1·2·4초로 3번. 쓰기는 자동 재시도하지 않는다(대기열 3가지 제외).
- `rev`: 받은 메뉴판의 `rev`가 가진 것보다 클 때만 갈아 끼움. 접속·재접속 때마다 `GET /state`. 401이면 토큰 지우고 `{ type:"signedOut" }` 신호.
- **진삼 조사(`docs/research/2단계_실시간.md`) 채택분**:
  - 소켓 접속은 함수형 `auth: (cb) => cb({ token, groupId })`. `connectionStateRecovery`는 쓰지 않는다.
  - `connect_error`(UNAUTHORIZED/FORBIDDEN)와 `disconnect` reason `"io server disconnect"`는 자동 재연결이 안 된다 → `socket.connect()`를 부르지 말고 토큰 지우고 `signedOut`.
  - `visibilitychange`(visible)·`pageshow`(persisted)·`online` 이벤트 때 `GET /state`(동시에 하나만). 실패하면 소켓 `disconnect().connect()`.
  - 오프라인 판정: `navigator.onLine === false`만 즉시 믿고, 나머지는 실제 요청 실패(네트워크 오류·타임아웃 8초)와 소켓 연결 여부로. 연결 확인용 가벼운 호출은 4.2 표에 있는 `GET /api/health`(`cache:"no-store"`).
  - 서버: 트랜잭션 함수 안에서 `await` 금지, prepare는 시작 때 한 번, `SIGINT`/`SIGTERM`에 `db.close()`. 백업은 3단계에서 `db.backup()`.
- **진육 E 리뷰 → 진록 결정 (E-2)**:
  - 필수1: 새로 받은 상태의 `today`가 캐시의 날짜와 다르면 rev와 상관없이 서버 값을 그대로 쓴다(자정 뒤 어제 확정이 오늘로 보이지 않게).
  - 필수2: 연결 중 **바로 보낸** 확정이 409면 대기열을 잠그지 않는다 — 반환값 `{ ok:false, code:"ALREADY_CONFIRMED", existing }`으로만 알린다. 잠금·`resolveConflict`는 대기열에서 나간 항목에만.
  - 필수3: 5xx·타임아웃·네트워크 오류는 대기열에서 **버리지 않고** 멈춘 뒤 다음 연결·다음 refresh 때 다시. 버리는 것은 400(오래된 날짜 등)뿐, 401은 signedOut, 403은 아래.
  - 권고1: 보낸 뒤 지울 때 맨 앞 항목 id가 보낸 항목과 같을 때만 지운다.
  - 권고2: 대기열이 비어 있지 않거나 보내는 중이면, 연결돼 있어도 대기열 3종류는 대기열로 넣어 순서를 지킨다.
  - 권고3: "어제 메뉴"로 옮기는 것은 캐시 날짜가 정확히 어제일 때만. 그보다 오래됐으면 어제 메뉴 없음(null).
  - 권고4: REST 403은 로그아웃하지 않고 `GET /state`로 다시 받는다. `GET /state` 자체가 403이거나 소켓 `connect_error` FORBIDDEN이면 그때 signedOut(설계 4.3).
  - 시험: 자정+같은 rev, 바로 보낸 409 뒤 대기열 정상 진행, 대기열 중 502 → 남아 있다가 다음에 성공, 위 권고 각각.
- **E-3 (진오 G 중 발견 → 진록 결정, E-2 재확인 끝난 뒤)**:
  - `store-remote`의 오류 결과에 서버의 `retryAfterSec`를 그대로 넘긴다(화면이 "{n}분 뒤에 다시 해 주세요" 표시).
  - Socket.IO 클라이언트 파일 불러오기에 실패해도 영구 오프라인으로 두지 않는다: REST는 계속 쓰고, 다음 refresh 계기(visibilitychange·online·30초 뒤 1번씩, 최대 5분 간격까지 늘림)에 다시 불러온다. 소켓이 없는 동안은 연결 끊김 띠를 보여 준다(실시간 반영이 안 되므로).
  - (진육 E-2 재확인) 바로 보내는 요청이 진행 중일 때도(`sendingDirect`) 대기열 3종류는 대기열로 넣어 순서를 지킨다(addSkip 직후 clearSkip이 뒤집히지 않게). 시험: 첫 요청을 늦게 보내는 가짜로 순서 확인.
  - `resolveConflict`는 충돌 난 항목의 id를 기억해 두고, 맨 앞이 그 id일 때만 덮어쓰기·지우기.
  - 바로 보낸 대기열 3종류가 403이면 버리지 않고 대기열에 넣은 뒤 `GET /state` — 로그인이 유지되면 다음에 다시 보내고, signedOut이면 대기열은 로그아웃과 함께 비운다.
  - 대기열이 5xx·네트워크 오류로 멈추면 연결이 유지돼도 30초 뒤부터(최대 5분 간격) 다시 보내 본다(소켓 파일 재시도와 같은 간격 규칙).
- **E-4 (진육 E-3 재확인 권고 → 진록 결정, E 커밋 확인 뒤)**: ① 확정은 언제나 "누른 날"(`todayKST()` 기준)을 `date`로 함께 보낸다(서버가 오늘·어제만 받으므로 23:59:59에 누른 것이 다음 날로 기록되지 않게). ② `today()`가 `cache.day`와 다르면(소켓 없이 자정을 넘긴 경우 등) refresh를 부른다. ③ (진육 H 새 권고2) 대기열에 아직 안 보낸 확정이 있으면 화면 계산에 반영한다 — 그 날짜가 오늘이면 오늘 확정·넘김 비움, 자정을 넘겨 어제가 됐으면 "어제 메뉴"로.
- G 설계 차이 승인: 확인창 `#overwriteRo`(조사 분리)·`#overwriteDay` 한 줄, "어제"는 대기열 `pending.date`로 판단(서버 변경 없음).
- 단위 시험 `tests/unit/outbox.test.js`, `store-remote.test.js`: 가짜 fetch·가짜 소켓·가짜 storage로 — 끊김 중 쌓기 → 재연결 시 순서대로 → 409 신호, 오래된 `rev` 무시·같은 이벤트 두 번 안전, 오프라인 편집 거부.
